# Квоты, расход и маршрутизация

## Политика выбора

Выбор аккаунта выполняет встроенный scheduler CLIProxyAPI. ProxCli ранжирует аккаунты каждого провайдера по ближайшему будущему сбросу известного общего окна квоты и обновляет только поле `priority`. При равном сбросе порядок стабилен по auth ID. `fill-first` выбирает верхний доступный приоритет для новой сессии. Положительный известный остаток предпочтительнее неизвестного; исчерпанные аккаунты получают низший приоритет. Disabled не включаются в ротацию.

Если аккаунт связан с диалогом, изменение приоритетов не меняет эту связь. Для сессий используются штатные механизмы CPA: явные ID клиента, родительские сессии и matcher общей истории (LCP). Scheduler-плагин не устанавливается: в v8.0.63 он обходит встроенную affinity.

В сборку ядра включён режим `session-affinity-rebind-on: quota-strict`:

- 5xx, сетевые сбои, 401/403, ошибки модели и обычный rate limit не отправляют запрос на другой аккаунт. Возвращается ошибка или выполняется разрешённый ядром retry того же аккаунта.
- Автоматический перенос допускается при подтверждённом исчерпании: credential-scoped quota или явная ошибка подписочного лимита, например `usage_limit_reached`/`quota_exhausted`. Один статус 429 без подтверждения не достаточен.
- После переноса создаётся новая привязка; восстановившийся прежний аккаунт не перетягивает сессию обратно.
- Model-specific квоты не считаются исчерпанием других моделей.

Квота подписки, лимит контекста и TTL кеша — независимы. По счётчику токенов нельзя определить конец диалога. TTL affinity в новом конфиге — 168 часов простоя с продлением при обращениях, а не таймер от начала диалога.

**Граница гарантии:** affinity штатного CPA живёт в памяти. Перезапуск самого ядра, изменение режима/TTL affinity, удаление аккаунта или истечение TTL могут потерять привязку. Перезапуск только панели сохраняет привязки работающего ядра. Долговечное восстановление всех явных и LCP-сессий после перезапуска ядра пока не реализовано. Пока идёт важный диалог, не перезапускайте ядро ради обновления UI.

Режим меняет поведение при ручном отключении привязанного аккаунта: сессия получает ошибку, а не незаметно переходит на другой аккаунт. Для переноса без исчерпания начните новую сессию клиента. Глобальные приоритеты не выражают разные предпочтения для каждой модели; модельные ограничения остаются ответственностью CPA.

## Сбор данных

Панель раз в минуту читает `GET /v8/management/credentials`. `quota.signals` — пассивные watermark заголовки, а не количество оставшихся токенов. После рестарта CPA они могут отсутствовать, поэтому последнее наблюдение сохраняется локально вместе с временем.

Для Claude и Codex выполняются фиксированные запросы к usage API через `POST /v8/management/requests/api-call` с `auth_index` и `$TOKEN$`. Токен подставляет CPA; запрос использует прокси соответствующей подписки. ProxCli не передаёт proxy override и не скачивает auth-файлы. Проверки ограничены одним запросом на аккаунт за 5 минут. Ошибка доступа, протухший токен или неполный ответ оставляют квоту неизвестной/устаревшей, а не обнуляют её.

Старше 10 минут наблюдение не используется для ранжирования. Прошедшее время reset само по себе не означает «снова 100%»: нужно новое наблюдение. Проценты разных окон не складываются в токены. Процент Claude из заголовка — доля 0…1, из usage API — 0…100; Codex использует used_percent 0…100.

## История

C ABI плагин `proxcli-usage` имеет только capability `usage_plugin`. Он наблюдает завершённые запросы и не потребляет общую destructive usage-queue. До очереди записи очищаются: сохраняются request ID, auth ID, provider/model, хеш сессии, timestamp, status и token counters. API key, session ID в исходном виде, ошибка upstream, cookies, прочие заголовки и тексты запросов не сохраняются. Из квотных заголовков сразу создаются типизированные окна.

Журнал `.data/telemetry` — отдельные дневные JSONL-файлы с правами 0600 и retention 30 дней. Запись выполняет отдельный worker. История различает ввод без кеша, output/reasoning, cache reads и cache writes; для Codex cached input вычитается из общего input, для Claude cache creation не подставляется вместо cache read. `total` берётся из upstream, счётчики повторно не суммируются. Request ID устраняет повторный учёт одного события при чтении. Запросы без usage не получают выдуманных токенов.

Observer имеет очередь 4096 событий. Переполнение и ошибки диска показываются счётчиками `dropped`/`writeErrors`; это не биллинговый журнал с гарантией exactly-once. При аварийном завершении процесса ещё не записанные события могут быть потеряны. При штатном завершении очередь сбрасывается на диск. Неполная последняя строка журнала не ломает чтение остальных записей.

События `first-observed-session` и `observed-account-change` — наблюдения по завершённым запросам. Они не доказывают причину переключения и не подменяются выдуманным «quota failover». Отдельные события `priority-updated` фиксируют работу контроллера.

## API панели

- `GET /api/quotas`: последние наблюдения, время обновления и ошибки аккаунтов.
- `POST /api/telemetry/refresh`, тело `{}`: запросить обновление, сохраняя rate limit probes.
- `GET /api/history?range=6h|24h|7d|30d&provider=claude|codex&authId=...`: часовые token buckets, наблюдения квот и последние изменения.
- `GET /api/routing`: проверенный статус политики, приоритеты и состояние observer.

На обычном CLIProxyAPI контроллер не пишет приоритеты под видом строгой гарантии: требуется capability marker сборки ProxCli и фактический routing-конфиг `fill-first` + affinity + `quota-strict`.

## Подключение к существующему хабу

1. Сохраните свой текущий конфиг и остановите хаб перед заменой ядра/observer.
2. Выполните `bun run build:core` в каталоге ProxCli.
3. В используемом конфиге установите:

```yaml
routing:
  strategy: fill-first
  session-affinity: true
  session-affinity-ttl: 168h
  session-affinity-rebind-on: quota-strict
plugins:
  enabled: true
  dir: /absolute/path/to/proxcli/bin/plugins
  configs:
    proxcli-usage:
      enabled: true
```

4. Запускайте `bin/cli-proxy-api -config <ваш-конфиг>` с `PROXCLI_DATA_DIR`, указывающим на тот же абсолютный каталог, что у панели. Для сгенерированного `.data/cliproxyapi.yaml` и запуска из корня подходит `bun run hub`.
5. В окружении панели задайте `PROXCLI_MANAGE_ROUTING=true` и management key этого хаба. Клиентам по-прежнему нужен только access key.
6. Убедитесь, что на странице статистики политика и observer активны. Квоты появляются после ответа провайдера или успешного usage probe, история — после новых запросов.

Ни `init`, ни контроллер не переписывают весь существующий конфиг. Контроллер изменяет только priority. Не подключайте другие scheduler-плагины: они могут обходить affinity. Такие комбинации не поддерживаются.
